# V0.7.0 — CI

Parent : [#99](https://github.com/UlyssouLV/workflow-agents-pack/issues/99)

## Problème

Sur le canal orchestrateur, une branche de version peut être proposée en PR vers `feat/runtime-orchestrator` sans qu’aucune vérification automatique ne tourne : pas de workflow GitHub Actions, pas de scan Sonar déclenché sur le HEAD de la PR. On ne sait pas vite si la branche est saine ; il faut relancer à la main pytest, Vitest, et éventuellement un scan Sonar. `/qg` lit déjà un quality gate Sonar, mais sans analyse produite par la CI pour ce commit, le gate n’est pas alimenté automatiquement. Rien n’empêche non plus de merger dans la base tant que les checks ne sont pas verts.

## Solution

Une **CI** sur chaque PR vers la base d’intégration `feat/runtime-orchestrator` : un workflow GitHub Actions avec jobs parallèles (pytest + couverture, Vitest + couverture), puis un job Sonar qui analyse `orchestrator/`, envoie la couverture, et **échoue** si le quality gate n’est pas `OK`. Les secrets Sonar du dépôt (même projet que `/qg`) sont documentés. Le README explique la CI, les secrets, et la **ruleset / protection de branche** à poser manuellement sur `feat/runtime-orchestrator` (checks requis) pour bloquer le merge tant que la CI n’est pas verte. Glossaire et ADR ancrent le vocabulaire et la décision. Pas de nouvelle capacité cockpit/runtime : le détail repo sait déjà signaler une CI en échec.

## User stories

1. En tant que développeur de l’orchestrateur, je veux que chaque PR vers la base d’intégration lance automatiquement les suites de tests, pour savoir vite si la branche est saine sans tout relancer à la main.
2. En tant que développeur, je veux que pytest tourne en CI avec couverture, pour garder le runtime comme `/t` en local et alimenter Sonar.
3. En tant que développeur, je veux que Vitest tourne en CI avec couverture, pour garder le cockpit et alimenter Sonar.
4. En tant que développeur, je veux un scan Sonar sur le HEAD de la PR en CI, pour que `/qg` et Finalise lisent un gate qui correspond à ce commit.
5. En tant que développeur, je veux que le job Sonar échoue si le quality gate n’est pas `OK`, pour qu’un gate rouge soit un check GitHub rouge.
6. En tant que développeur, je veux que la CI tourne sur toute PR vers `feat/runtime-orchestrator` (sans filtre de chemins), pour un verdict prévisible sur ce canal.
7. En tant que développeur, je ne veux pas de CI pack sur `main` dans cette version, pour rester sur le canal orchestrateur.
8. En tant que mainteneur, je veux la doc des secrets Sonar GitHub (alignés sur `/qg`), pour que Actions analyse le même projet.
9. En tant que mainteneur, je veux une ruleset / protection documentée sur `feat/runtime-orchestrator` avec les checks CI requis, pour qu’une CI rouge ne puisse pas merger dans la base.
10. En tant que mainteneur, je veux poser ou vérifier cette ruleset à la main (pas un script d’API dans le repo), pour que les droits admin GitHub restent la source de vérité.
11. En tant qu’opérateur qui lit le cockpit, je veux que « CI en échec » continue de signifier des checks échoués sur la PR de version, pour que l’intervention humaine reste cohérente une fois Actions en place.
12. En tant que développeur, quand la CI est rouge, je veux corriger les raisons (tests ou conditions Sonar) jusqu’au vert, pour que la branche redevienne acceptable.
13. En tant que lecteur de la doc, je veux une entrée glossaire **CI**, pour ne pas confondre Actions, `/t` local et `/qg` seul.
14. En tant que lecteur futur, je veux un ADR qui ancre « CI = Actions sur les PR vers la base + Sonar dans le même pipeline », pour que le choix ne soit pas surprenant.
15. En tant que développeur, je veux un `sonar-project.properties` (ou équivalent) borné à `orchestrator/`, pour analyser le code produit, pas tout l’arbre pack.
16. En tant que développeur, je veux des jobs de tests en parallèle puis Sonar, pour un feedback rapide et des artefacts de couverture avant le scan.
17. En tant que responsable de release, je veux que le CD / publish / deploy reste hors de cette version, pour que 0.7.1 porte ce job.
18. En tant que développeur, je veux que la CI garde l’approche faux `docker` des suites (pas de Docker Engine réel requis dans Actions), pour la même couture qu’en local.

## Décisions d’implémentation

- **Déclencheur** : `pull_request` vers `feat/runtime-orchestrator` uniquement (pas la CI pack sur `main` en 0.7.0).
- **Sans filtre de chemins** : toute PR vers la base lance la CI complète.
- **Forme du workflow** : un workflow ; jobs parallèles tests Python (couverture) et cockpit (couverture) ; puis job Sonar qui consomme les artefacts et échoue si le gate ≠ `OK`.
- **Runtimes** : Python 3.12 pour pytest ; Node adapté à la toolchain cockpit du dépôt.
- **Sonar** : même projet que `/qg` (secrets Actions `SONAR_*`) ; secrets documentés ; pas de rotation automatique.
- **Périmètre d’analyse** : `orchestrator/` (exclusions tests/vendor raisonnables).
- **Couverture** : collecter et envoyer la couverture pytest et Vitest.
- **Protection de branche** : documenter les noms des checks requis ; un humain pose / vérifie la ruleset sur `feat/runtime-orchestrator`. Pas de script d’API dans le repo.
- **Code produit** : pas de nouvelle feature cockpit/runtime ; version du paquet `0.7.0`.
- **Doc** : section README CI (quand ça tourne, secrets, ruleset) ; glossaire **CI** ; ADR 0012.
- **CI rouge** : corriger jusqu’au vert (`/cqg` si c’est le gate).

## Décisions de test

- Bon test = comportement observable aux coutures : conclusions des checks GitHub sur une PR vers la base ; suites locales toujours vertes avec couverture ; étapes secrets/ruleset actionnables par un humain.
- **Couture principale** : checks de la PR (jobs pytest, Vitest, Sonar) — vert/rouge = succès des suites et gate Sonar.
- **Couture locale** : mêmes points d’entrée pytest / Vitest que `/t`, plus production de couverture utilisée par la CI.
- **Pas de nouvelle couture HTTP produit** dans cette version.
- Suites 0.1.0–0.6.0 restent vertes.
- Tests humains : observer les checks sur une PR vers la base ; confirmer les secrets ; poser ou vérifier que la protection bloque le merge tant qu’un check requis est rouge/pending ; README aligné.

## Hors périmètre

- CD, publication ou déploiement automatiques (0.7.1).
- CI du pack sur `main`.
- Lint / format comme jobs requis séparés.
- Docker Engine réel dans Actions pour les suites (faux `docker` conservé).
- Pose automatique de la ruleset via un script du repo.
- Nouvelle UI cockpit ou comportement runtime au-delà de la lecture existante « CI en échec ».
- Migration de projet Sonar ou changement d’hôte.

## Notes

- `/qg` continue de *lire* le gate ; la 0.7.0 fait *produire* l’analyse en CI pour le HEAD de la PR.
- La ruleset est un réglage admin GitHub ; la version livre des checks stables et la doc, pas l’application API.
