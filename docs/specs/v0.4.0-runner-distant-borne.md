# V0.4.0 — Runner distant borné

## Problème

Après la 0.3.0, le cockpit montre où en est chaque repo lié (version ouverte, progression, étape, intervention humaine requise), mais il ne fait rien : pour implémenter le ticket suivant, l’utilisateur doit ouvrir son propre poste, cloner ou mettre à jour le repo, lancer Claude Code ou Cursor et taper `/implement #n`. La machine hôte a déjà les CLIs agents (0.2.0) et une identité GitHub (0.3.0), mais aucun moyen de les faire travailler sur un repo métier, ni de suivre ce travail depuis le cockpit.

## Solution

Depuis la vue détail d’un repo, l’utilisateur choisit un **agent** (Claude Code ou Cursor) et clique **`/implement #n`** sur un enfant éligible. Un nouveau service **`runner`** de l’instance prépare un **clone géré** du repo sur la branche de la PR de version, puis lance l’agent **en mode interactif** dans un **vrai terminal**, affiché dans le navigateur : l’utilisateur y suit le travail et y tape le workflow des skills exactement comme en local (`/clear`, `/implement #suivant`, réponses aux questions…). L’orchestrateur reproduit le workflow actuel ; il n’ajoute pas de boutons de workflow.

Chaque **session** est enregistrée (terminal + transcription de l’agent) et se **rejoue** depuis le cockpit. Une seule session ouverte à la fois sur l’instance.

```bash
sudo wap-runtime auth claude                 # Claude Code (setup-token), ou --with-token
sudo wap-runtime auth agent --with-token     # Cursor (clé API)
sudo wap-runtime auth status                 # GitHub, Claude, Cursor
ssh -L 8787:127.0.0.1:8787 mon-serveur       # puis http://127.0.0.1:8787/
```

## User stories

1. En tant qu’utilisateur, je connecte Claude Code avec `sudo wap-runtime auth claude` (code à valider dans mon navigateur) ou un token sur stdin, et Cursor avec `sudo wap-runtime auth agent --with-token` ; je me reconnecte de la même façon après une révocation.
2. En tant qu’utilisateur, `auth status` et l’encart **Agents** du cockpit me disent quels agents sont connectés, avec la commande à lancer pour ceux qui ne le sont pas.
3. En tant qu’utilisateur, sur la vue détail d’un repo, je choisis l’agent et je vois un bouton **`/implement #n`** sur chaque enfant éligible ; un bouton grisé me dit pourquoi (enfant bloqué, déjà `in-agent-test`, pas de PR de version, session déjà ouverte, agent non connecté).
4. En tant qu’utilisateur, je clique `/implement #n` : un terminal s’ouvre dans le cockpit, l’agent démarre sur `/implement #n` dans le clone géré, sur la branche de la PR de version, et je peux taper dedans comme en local.
5. En tant qu’utilisateur, je ferme l’onglet puis reviens : la session tourne toujours et je retrouve l’écran. Un deuxième onglet voit la session en lecture seule.
6. En tant qu’utilisateur, si le clone a des changements non commités (session précédente échouée), le cockpit me les montre avant de lancer et me laisse **Reprendre** sur cet arbre ou **Jeter** (le diff est gardé dans le dossier de la session).
7. En tant qu’utilisateur, quand l’agent a fini, je tape la suite du workflow des skills (`/clear`, `/implement #suivant`) dans le même terminal, ou je ferme la session (`/exit` ou **Terminer**).
8. En tant qu’utilisateur, je vois la liste des sessions d’un repo (date, agent, commande, état) et je rejoue une session terminée.
9. En tant qu’utilisateur, la vue liste m’indique par un badge le repo qui a une session ouverte ; un deuxième lancement est refusé avec un lien vers la session ouverte.
10. En tant qu’utilisateur, les commits poussés par une session apparaissent sous le compte GitHub de l’instance, avec l’agent en co-auteur.
11. En tant qu’utilisateur, si le runner redémarre pendant une session, elle apparaît **interrompue** et je peux en lancer une nouvelle.

## Décisions d’implémentation

- **Service `runner`** : nouveau service de la Compose de l’instance, image construite localement (même contexte que `runtime`, ADR 0002).
  - Contient `git`, `gh`, `claude` (npm, **version épinglée**), `agent` (archive Cursor de la **version épinglée**, vérifiée par empreinte SHA-256 par architecture), Python 3 + venv, Node, `tmux`, et les **skills de Matt Pocock** installés par la CLI `skills` à un **commit épinglé**, en portée utilisateur (comme `~/.agents/skills` lié dans `~/.claude/skills` et `~/.cursor/skills`). Les skills du pack viennent du clone (`.claude/`, `.cursor/`, `agents/`, `AGENTS.md`).
  - Tourne avec l’**UID d’`orchestrator`** ; **pas de socket Docker** ; `HOME` persistant dans l’instance (`runner-home/` : historique, identifiants et transcriptions des agents survivent aux redémarrages).
  - Monte en écriture `clones/`, `jobs/` et `runner-home/` de l’instance, rien d’autre ; reçoit `secrets.env` par `env_file`.
  - API interne **non publiée** : le `runtime` lui parle sur le réseau Compose et relaie le terminal (websocket).
  - ADR 0004.
- **Clone géré** : `~/.wap-runtime/clones/<owner>/<name>/`, créé au premier lancement (HTTPS, `GH_TOKEN`, `gh auth setup-git`). Avant chaque session : `fetch`, passage sur la branche de la PR de version (refus sans PR). Pas de remise à zéro automatique : changements non commités → le lancement demande **Reprendre** (session sur cet arbre) ou **Jeter** (`git diff` + fichiers non suivis enregistrés dans `jobs/<id>/abandon.patch`, puis `reset --hard` + `clean -fd`). `repo remove` ne supprime pas le clone.
- **Identité git** : `user.name` = login du compte de `GH_TOKEN`, `user.email` = son adresse noreply GitHub ; l’agent se met en co-auteur (`Co-Authored-By`) selon son comportement par défaut.
- **Auth des agents** :
  - `wap-runtime auth claude` : `claude setup-token` **en tant qu’utilisateur d’instance sur l’hôte** (CLI installée en 0.2.0), token écrit dans `secrets.env` sous `CLAUDE_CODE_OAUTH_TOKEN` ; `--with-token` lit un token sur stdin (`ANTHROPIC_API_KEY` accepté) ;
  - `wap-runtime auth agent --with-token` : clé API Cursor sur stdin, écrite sous `CURSOR_API_KEY` (`agent login` exige un navigateur local) ;
  - `wap-runtime auth` sans argument reste la connexion GitHub (0.3.0) ; `auth status` affiche GitHub, Claude et Cursor ;
  - chaque écriture redémarre les services (`env_file` lu au démarrage) ; idempotent ; le setup **n’enchaîne pas** sur l’auth des agents, il l’indique comme prochaine étape.
  - « Connecté » = token présent (pas d’appel de vérification) ; un refus de l’agent s’affiche dans son terminal.
- **Éligibilité du bouton `/implement #n`** : enfant ouvert, `ready-for-agent`, non bloqué (`issue_dependencies_summary.blocked_by` = 0), sans `in-agent-test` ; PR de version ouverte ; aucune session ouverte sur l’instance ; agent choisi connecté. Sinon grisé avec la raison.
- **Lancement** : `POST /api/sessions` (`repo`, `ticket`, `agent`, choix Reprendre / Jeter si demandé) ; le serveur refuse toute requête d’action dont l’en-tête `Origin` n’est pas celui du cockpit servi (pas de CORS) ; deuxième session → `409` avec le lien de la session ouverte.
- **Terminal** : l’agent est lancé **en mode interactif** (`claude "/implement #n"`, `agent "/implement #n"`) dans une session **tmux** du `runner` ; le cockpit l’affiche avec **xterm.js** par websocket. Fermer l’onglet ne tue pas la session ; un seul client écrit (le premier connecté), les autres sont en lecture seule. **Terminer** arrête l’agent et ferme la session. Aucun bouton « suivant » : le workflow des skills se tape dans le terminal.
- **Borné** : une seule session **ouverte** sur l’instance ; pas de délai imposé ; **Terminer** toujours disponible.
- **États d’une session** : `ouverte`, `terminée` (sortie 0), `échouée` (sortie ≠ 0), `interrompue` (runner redémarré pendant la session — marquée au démarrage du runner).
- **Labels** : le runner **ne pose aucun label**. Le hook du pack qui posera `in-agent-test` (#24, sur `main`) vivra dans le repo métier, donc aussi dans le clone du runner.
- **Enregistrement** : `~/.wap-runtime/jobs/<id>/` contient `session.json` (repo, ticket, agent, commande, début, fin, état, code de sortie), `terminal.cast` (asciinema v2) et la transcription native de l’agent copiée à la fin. Jamais de suppression automatique.
- **Cockpit** :
  - encart **Agents** (Claude Code / Cursor : Connecté / Non connecté + commande) ;
  - vue détail : sélecteur d’agent, bouton `/implement #n` par enfant, liste des sessions du repo ;
  - page **`/sessions/<id>`** : terminal en direct (session ouverte) ou relecture du `.cast` (session finie), état, durée, Terminer ;
  - vue liste : badge **Session en cours**.
- **Instance** : `setup` crée `clones/`, `jobs/`, `runner-home/` (propriétaire `orchestrator`) et régénère la Compose avec `runner` ; `uninstall --purge` les supprime avec l’instance. Le `runtime` garde l’instance en lecture seule, sauf ce dont il a besoin pour lire `jobs/`.
- **Rien de global à la machine** : clones, sessions, tokens et `HOME` du runner propres à l’instance ; aucun nouveau port publié.
- **Version** du paquet : `0.4.0`.
- **Docs** : ADR 0004 (runner en conteneur, agents en interactif) ; glossaire (*runner*, *clone géré*, *session*) ; README (auth des agents, lancer `/implement`, sessions).

## Décisions de test

- **pytest, frontière HTTP** (FastAPI en process, faux GitHub, faux runner ou runner en process avec une **fausse CLI agent** dans le `PATH`) :
  - éligibilité et raisons de grisé ; refus d’une deuxième session (`409`) ; refus sans `Origin` du cockpit ;
  - clone créé au premier lancement, branche de la PR ; clone sale → choix demandé ; Reprendre ; Jeter (patch enregistré, arbre propre) ;
  - commande lancée selon l’agent (`claude` / `agent`, `/implement #n`) ;
  - états `terminée` / `échouée` selon le code de sortie, `interrompue` après redémarrage ; `session.json`, `terminal.cast`, transcription copiée ;
  - liste des sessions d’un repo ; badge dans la liste ; encart Agents selon `secrets.env`.
- **pytest, CLI** : `auth claude` avec un faux `claude` dans le `PATH` (token dans `secrets.env` en `0600`, redémarrage demandé, `--with-token`) ; `auth agent --with-token` ; `auth status` à trois lignes ; `auth` GitHub inchangé.
- **pytest, instance** : Compose contient `runner` (UID d’`orchestrator`, montages `clones/`, `jobs/`, `runner-home/`, pas de socket Docker, aucun port publié) ; `setup` crée les dossiers ; `uninstall --purge` les supprime.
- **Vitest** : encart Agents, sélecteur et boutons (éligible / grisé + raison), liste des sessions, page de session (terminal en direct vs relecture) à partir de réponses `/api/` simulées.
- Les suites des versions 0.1.0 à 0.3.0 restent vertes.
- Vraies sessions Claude Code et Cursor, terminal par tunnel SSH, push réel : ticket de tests humains.

## Hors périmètre

- Autres skills que `/implement` depuis le cockpit (Ouvre la version, `/th`, `/code-review`, Finalise, `/cqg`, session libre) : 0.4.2.
- États « en train de travailler » / « réponse attendue » (hooks des agents) : 0.4.2.
- Plusieurs sessions ouvertes à la fois, parallélisme.
- Poser / retirer les labels d’état (`in-agent-test`, `in-human-test`) : hook du pack, #24.
- Boutons de workflow (« suivant »…), enchaînement automatique des tickets (autopilot).
- Détecter les sessions locales des postes (Claude Code / Cursor hors serveur).
- Outils de projet autres que Python et Node dans l’image du runner.
- Instances multiples, accès web authentifié, exposition hors `127.0.0.1`.
