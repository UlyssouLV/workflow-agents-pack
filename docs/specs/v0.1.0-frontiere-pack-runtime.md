# V0.1.0 — Frontière pack / runtime

## Problème

La branche `feat/runtime-orchestrator` sert à développer l’orchestrateur, mais elle versionne une copie complète du pack de skills (`agents/skills/`, `agents/hooks/`, `agents/scripts/`, `.claude/skills/`, `.cursor/skills/`). Cette copie dérive de `main`, où le pack est réellement maintenu : rien n’indique qu’on ne doit pas la modifier ici, et la mettre à jour produit des diffs sans rapport avec l’orchestrateur. Le README de la branche décrit le pack et non l’orchestrateur, et il n’existe ni zone de code `orchestrator/`, ni suite de tests, ni `AGENTS.md`, ni glossaire, ni dossier d’ADR ou de specs.

## Solution

Sur cette branche, le pack devient un **outil installé**, comme dans n’importe quel projet qui l’adopte : ce que la commande de mise à jour du pack régénère est ignoré par git, et le développeur l’installe ou le met à jour lui-même depuis `main` avec `update-from-pack.sh`. Le dépôt ne suit que la configuration propre au projet. `orchestrator/` est la seule zone de développement ; une première suite pytest y garde la frontière. Le README racine présente l’orchestrateur. La branche n’est jamais fusionnée dans `main`.

## User stories

1. En tant que développeur de l’orchestrateur, je clone la branche, j’installe les skills depuis `main` avec une commande documentée, et je peux travailler avec `/implement`, `/t`, etc.
2. En tant que développeur de l’orchestrateur, quand les skills évoluent sur `main`, je relance la même commande et mon `git status` reste propre.
3. En tant que développeur, si un `.gitignore` élargi par erreur fait sortir la config du projet de git (ou y fait entrer le pack), `/t` échoue.
4. En tant que lecteur de la branche, le README me dit ce qu’est l’orchestrateur, sa trajectoire (0.1 → 0.6), comment préparer l’environnement de dev, et que le pack se maintient sur `main`.
5. En tant qu’agent, `AGENTS.md` me dit de ne pas modifier le pack ici, que la branche n’est jamais fusionnée dans `main`, et où vit le code.

## Décisions d’implémentation

- **Ignorés par git** (et retirés de l’index avec `git rm --cached`) : `agents/skills/`, `agents/hooks/`, `agents/scripts/`, `.claude/skills/`, `.cursor/skills/` — exactement ce que `update-from-pack.sh` + `dispatch.py` régénèrent ; plus `agents/templates/`, ancienne copie que `update-from-pack.sh` supprime (les modèles sont lus dans le pack).
- **Restent suivis** : `agents/roles.yml`, `agents/integration-channel.yml`, `agents/issue-tracker.md`, `agents/domain.md`, `agents/triage-labels.md`, `agents/docs/`, `agents/README.md`, `.claude/CLAUDE.md`, `.claude/settings.json`, `.claude/hooks/`, `.cursor/hooks.json`, `.cursor/hooks/`. (`.claude/hooks/gate-code-review.py` reste suivi : la mise à jour ne le rafraîchit pas, voir bug #3 sur `main`.)
- **Installation sur un clone neuf** : `mkdir -p agents/skills`, cloner le pack depuis `main` dans un dossier temporaire, lancer `update-from-pack.sh` depuis la racine. Mise à jour courante : même commande sans le `mkdir`. Aucun changement sur `main`.
- **Outillage de test** : Python 3.12, `orchestrator/requirements-dev.txt` (pytest), `orchestrator/pytest.ini`, venv `orchestrator/.venv` (déjà ignoré par `.venv/`). Pas de `pyproject.toml` tant que le runtime n’existe pas. Rôle `test-roots` → `orchestrator/` dans `agents/roles.yml`.
- **README racine** réécrit pour l’orchestrateur. Pas de second README sous `orchestrator/`.
- **Rôles créés** : `docs/specs/` (cette spec), `docs/adr/0001-pack-outil-installe-sur-la-branche-orchestrateur.md`, `docs/glossaire.md` (pack, runtime, cockpit, machine hôte, instance, repo métier), `AGENTS.md` racine propre à la branche.
- **Feuille de route** : objectif et hors périmètre de la 0.1.0 réécrits (fait à l’initialisation de la version).

## Décisions de test

- `orchestrator/tests/test_frontiere_pack.py`, via `git check-ignore` lancé depuis la racine du dépôt :
  - chaque chemin régénéré par le pack est ignoré ;
  - chaque fichier de config du projet listé ci-dessus n’est pas ignoré ;
  - `orchestrator/` n’est pas ignoré.
- On teste le comportement observable de git (ignoré / pas ignoré), pas le contenu textuel du `.gitignore`.
