# V0.5.1 — Modèle Cursor par session

## Problème

Depuis la 0.4.2 / 0.5.0, on lance Cursor (session libre, enchaînement pack, Pilote) via la CLI `agent` **sans** choisir de modèle : le défaut opaque de la CLI s’applique. L’utilisateur ne voit pas quel modèle tourne, ne peut pas en fixer un pour un repo, et une chaîne Implement ne garantit pas la continuité du modèle choisi au premier lancement.

## Solution

Pour Cursor uniquement : une **préférence modèle par repo** (liste dynamique des modèles disponibles + **Auto**), un **override** optionnel à **Nouvelle session**, passage de `--model <id>` à la CLI (sauf Auto / vide), **héritage du modèle via `precedente`** pour l’enchaînement et affichage du modèle dans le cockpit (préférences + sessions). Le Pilote sans prédécesseur retombe sur la préférence repo.

## User stories

1. En tant qu’utilisateur, sur le détail d’un repo dont l’agent préféré est Cursor, je choisis un modèle dans un select (liste issue de `agent models`, avec Auto) ; ce choix est persisté dans le registry du repo.
2. En tant qu’utilisateur, tant que Cursor n’est pas connecté, je ne vois pas le select modèle.
3. En tant qu’utilisateur, si Cursor est connecté mais que la liste des modèles échoue, je ne peux pas lancer une session Cursor (message clair) — pas de lancement « à côté » de mon intention.
4. En tant qu’utilisateur, si le modèle mémorisé (préférence ou héritage) n’est plus dans la liste actuelle, le lancement Cursor est bloqué avec un message clair.
5. En tant qu’utilisateur, à **Nouvelle session** avec Cursor, le select est prérempli avec la préférence repo ; je peux overrider pour *cette* session sans modifier le défaut repo.
6. En tant qu’utilisateur, Auto (ou préférence vide) lance `agent` **sans** `--model` (défaut CLI).
7. En tant qu’utilisateur, un autre modèle passe `--model <id>` à la CLI Cursor.
8. En tant qu’utilisateur, une session enchaînée (`precedente`) reprend le modèle de la session précédente (même règle pour pack `enchainer` et pour la continuité d’une chaîne).
9. En tant qu’utilisateur, le Pilote qui démarre une session **sans** prédécesseur utilise la préférence repo (fallback).
10. En tant qu’utilisateur, je vois le modèle sur les préférences repo et sur la fiche / liste des sessions ; sans `--model`, le libellé affiché est **« Auto »**.
11. En tant qu’utilisateur, si l’agent est Claude, aucun sélecteur ni champ modèle n’apparaît.

## Décisions d’implémentation

- **Préférence repo** : champ modèle Cursor dans `repos.toml` (par `[[repos]]`), éditable seulement depuis les préférences du détail (comme `agent` / `pilote`) — jamais écrit automatiquement au lancement d’une session.
- **Liste** : endpoint runtime qui interroge `agent models` (ou équivalent) dans le contexte auth Cursor de l’instance ; UI absente si non connecté ; échec liste → bloquer lancement Cursor.
- **Lancement** : `commande_agent` accepte un modèle optionnel ; si présent et non-Auto → `agent --model <id> …` ; Auto / absent → argv actuel.
- **Résolution du modèle au lancement** : (1) override explicite Nouvelle session si fourni ; (2) sinon si `precedente` → modèle de cette session ; (3) sinon préférence repo ; (4) sinon Auto (pas de `--model`).
- **`session.json`** : enregistre le modèle effectif (ou marqueur Auto) pour affichage et héritage.
- **Enchaînement** : `enchainer` / `_ouvrir_suivante` lit le modèle de la session précédente, pas un override libre.
- **Pilote** : pas d’UI au lancement auto ; utilise la résolution ci-dessus (sans override) → en pratique préférence repo quand pas de `precedente`.
- **ADR** : préférence repo vs héritage chaîne (ne pas écrire le défaut au lancement) — ADR 0009.
- **Glossaire** : préciser le modèle Cursor (préférence + héritage `precedente`).
- **Version** du paquet : `0.5.1`.
- **Docs** : README (choix du modèle Cursor).

## Décisions de test

- **pytest, registry** : lire/écrire préférence modèle ; pas d’écriture au lancement.
- **pytest, agents / runner** : `--model` présent ou absent ; héritage via `precedente` ; fallback repo ; ID hors liste → refus.
- **pytest, HTTP** : liste modèles (connecté / non / échec) ; POST session avec modèle ; champs exposés détail + sessions.
- **pytest, pilote** : lancement sans prédécesseur utilise la préférence repo.
- **Vitest** : select visible seulement si Cursor connecté + agent Cursor ; préremplissage ; override Nouvelle session ; affichage « Auto » ; blocage si liste en échec.
- Suites antérieures vertes.
- Tests humains : choisir un modèle, lancer libre, enchaîner, vérifier continuité ; Pilote avec préférence ; Auto ; Cursor déconnecté / liste en échec.

## Hors périmètre

- Choix de modèle pour Claude Code.
- Changer de modèle au milieu d’une session déjà ouverte.
- Catalogue / quotas Cursor côté produit (au-delà de la liste renvoyée par la CLI).
- Instances multiples, accès web, refonte graphique (versions suivantes).
