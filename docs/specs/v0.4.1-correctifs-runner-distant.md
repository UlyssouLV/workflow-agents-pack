# V0.4.1 — Correctifs du runner distant (tests humains 0.4.0)

## Problème

Les tests humains de la 0.4.0 ([#34](https://github.com/UlyssouLV/workflow-agents-pack/issues/34)) montrent qu’une session lancée depuis le cockpit ne suit pas le workflow du pack, et que l’instance ne s’installe ni ne se connecte avec les commandes affichées :

- l’agent du runner n’a pas les skills du pack : il implémente puis s’arrête sans `/t`, push ni `/cci`, ou improvise avec des fichiers d’une autre branche (#40) ;
- `sudo wap-runtime auth claude` ne trouve pas la CLI `claude` installée par `setup` (#41) ;
- paquet et images sont construits depuis `feat/runtime-orchestrator` en dur : une version ne se teste pas sur un serveur avant sa fusion (#42) ;
- `sudo wap-runtime …`, affiché par le cockpit et `setup`, répond « commande introuvable » (#43) ;
- un onglet qui quitte la page de session garde la main sur le terminal : personne d’autre ne peut taper (#44) ;
- quand `encadrer-implement` enchaîne le ticket suivant, il ouvre un Terminal.app macOS : dans le runner, l’enchaînement échoue et le workflow s’arrête au premier ticket.

## Solution

Le runner prépare le clone géré avec les skills du repo et permet à la session d’enchaîner sur le ticket suivant dans une **nouvelle session** (contexte vierge) ; le cockpit libère et transfère la main ; l’installation se fait depuis un ref choisi et ses commandes se lancent telles quelles.

```bash
# Tester une branche de version avant fusion
curl -fsSL https://raw.githubusercontent.com/UlyssouLV/workflow-agents-pack/<ref>/orchestrator/install.sh \
  | sudo WAP_REF=<ref> bash
sudo wap-runtime auth claude        # trouvé dans le PATH de root, trouve `claude`
```

## User stories

1. En tant qu’utilisateur, une session `/implement #n` lancée depuis le cockpit sur un repo qui suit `agents/skills/` dispose des skills du pack à la version de la branche, sans fichier suivi modifié dans le clone.
2. En tant qu’utilisateur, sur un repo qui ne suit pas `agents/skills/`, la session démarre telle quelle (pas d’initialisation forcée du pack).
3. En tant qu’utilisateur, `sudo wap-runtime auth claude` trouve la CLI `claude` installée par `setup`, quel que soit mon PATH ; si elle manque, un `KO` me dit de relancer `setup`.
4. En tant qu’utilisateur, j’installe une instance depuis une branche de version (`WAP_REF=<ref>`) et les images de l’instance sont construites depuis le même commit que le paquet installé ; sans `WAP_REF`, c’est la base d’intégration.
5. En tant qu’utilisateur, je copie une commande `sudo wap-runtime …` affichée par le cockpit, `setup` ou le README, et elle se lance telle quelle sur l’hôte.
6. En tant qu’utilisateur, quand je quitte la page d’une session (vers la liste ou la vue détail), la main est libérée ; un autre onglet peut taper.
7. En tant qu’utilisateur, sur un onglet en lecture seule, l’écran me dit qu’un autre onglet a la main et un bouton **Prendre la main** me la donne ; l’autre onglet passe en lecture seule et le voit.
8. En tant qu’utilisateur, quand `encadrer-implement` enchaîne sur `/implement #m` dans une session du cockpit, la session courante passe **enchaînée** et une nouvelle session démarre sur `#m` (même repo, même branche, même agent, contexte vierge) ; mon onglet la suit et garde la main s’il l’avait.
9. En tant qu’utilisateur, la liste des sessions du repo et la page d’une session montrent la chaîne (précédente / suivante).

## Décisions d’implémentation

- **Skills dans le clone (#40)** : après le positionnement du clone et avant l’agent, si le clone a `agents/skills/` **et** `agents/scripts/dispatch.py`, le runner lance `python3 agents/scripts/dispatch.py` dans le clone. Sinon, rien (pas de montage du pack de l’instance, pas d’`update-from-pack.sh`). Dispatch en échec (code ≠ 0), ou fichier suivi modifié après le dispatch → `RunnerErreur`, l’agent n’est pas lancé. Vaut pour toute session, enchaînée ou non.
- **PATH hôte (#41)** : une fonction commune à `socle._detecter` et `agents._setup_token` construit le PATH de l’hôte = PATH de l’appelant + `/usr/local/sbin:/usr/sbin:/sbin` + `~orchestrator/.local/bin`, et résout `claude` et `runuser` en chemins absolus. Introuvable → `KO — claude introuvable : relance sudo wap-runtime setup`.
- **Ref d’installation (#42)** : `install.sh` lit `WAP_REF` (défaut : `feat/runtime-orchestrator`, la base d’intégration) pour `PAQUET`. `setup` lit le ref des images dans le paquet installé (`direct_url.json`, PEP 610 : `commit_id`, sinon `requested_revision`) ; sans `direct_url` VCS (installation locale ou éditable) → ref par défaut. Le contexte de build de `runtime` et `runner` en découle (`…git#<ref>:orchestrator`). À vérifier en implémentation : BuildKit accepte un SHA complet comme ref ; sinon `requested_revision`. ADR 0005.
- **Lien `wap-runtime` (#43)** : `setup` (root) crée `/usr/local/bin/wap-runtime → ~orchestrator/.local/bin/wap-runtime` (dans le `secure_path` de sudo) ; un fichier existant qui n’est pas ce lien → `KO` sans écraser. `uninstall` retire le lien s’il est le nôtre. Les messages gardent le nom court ; le README revient au nom court. Relancer `setup` répare une instance 0.4.0.
- **Main sur le terminal (#44)** :
  - quitter la page de session ferme le websocket du terminal (cause exacte à diagnostiquer : page gardée en mémoire, composant non démonté), le runner libère la main ;
  - nouveau message client → serveur `{"prendre": true}` : le client devient écrivain, l’ancien écrivain repasse en lecture seule (`{"role": "lecture"}`) ; toujours un seul écrivain ; la règle « le plus ancien prend la main au départ de l’écrivain » reste ;
  - cockpit : en lecture seule, « Lecture seule : un autre onglet a la main. » et un bouton **Prendre la main**.
- **Enchaînement** :
  - le runner lance chaque agent avec `WAP_ENCHAINER=wap-runtime enchainer` et `WAP_SESSION_JETON=<jeton>` (aléatoire, propre à la session) dans son environnement ;
  - `wap-runtime enchainer <n>` (dans l’image du runner) appelle l’API interne du runner (même conteneur) : `POST /sessions/<id>/suivante {ticket, jeton}` ;
  - le runner refuse si le jeton n’est pas celui de la session **ouverte**, s’il a déjà servi (usage unique), ou si `#n` n’est pas un enfant **éligible** du même repo (mêmes règles que le bouton du cockpit, hors « session déjà ouverte ») ; clone sale → refus. Le refus s’affiche à l’agent (sortie ≠ 0) : le skill passe à son fallback ;
  - accepté : réponse à l’agent, **puis** la session courante passe `enchaînée` (tmux arrêté) et une nouvelle session démarre sur `/implement #n`, même repo, même branche, même agent, **nouveau processus** sans `--continue` / `--resume` (contexte vierge) ;
  - aucune autre commande, aucun autre repo, aucun changement d’agent n’est possible par ce chemin ;
  - `session.json` gagne `precedente` / `suivante` ; nouvel état `enchaînée` ;
  - cockpit : la page d’une session enchaînée suit la suivante (bandeau « Session enchaînée : /implement #m »), l’onglet écrivain garde la main ; la liste des sessions du repo montre la chaîne ;
  - fin de chaîne : rien de nouveau, la session reste ouverte jusqu’à **Terminer** (la fin d’`encadrer-implement` demande une action humaine) ;
  - nouvel ADR 0006 : une session peut demander au runner d’en ouvrir une autre (frontière de l’ADR 0004).
- **Pack (hors version, sur `main`)** : `enchainer-implement.sh` exécute `$WAP_ENCHAINER <n>` quand la variable existe, avant le test macOS ; `encadrer-implement` le mentionne. Suivi par un bug sur `main`, hors sous-issues de cette version (ADR 0001 : le pack ne se modifie pas sur cette branche). Sans pack à jour, l’enchaînement retombe sur le fallback actuel.
- **Version** du paquet : `0.4.1`.
- **Docs** : ADR 0005 (ref d’installation), ADR 0006 (enchaînement de sessions) ; glossaire (*Main*, *Session enchaînée*) ; README (`WAP_REF`, nom court, prendre la main, enchaînement).

## Décisions de test

- **pytest, runner** (clone local, fausse CLI agent) : dispatch lancé quand `agents/skills/` et `dispatch.py` existent (skills présents sous `.claude/skills/` et `.cursor/skills/`, aucun fichier suivi modifié) ; aucun dispatch sans eux, l’agent démarre ; dispatch en échec → pas de lancement.
- **pytest, enchaînement** : jeton valide + enfant éligible → session courante `enchaînée`, nouvelle session `/implement #m` même agent / branche, sans option de reprise, `precedente` / `suivante` ; refus : mauvais jeton, jeton réutilisé, enfant non éligible, autre repo, clone sale ; `wap-runtime enchainer` rend ≠ 0 sur refus.
- **pytest, terminal** : `{"prendre": true}` transfère la main, l’ancien écrivain reçoit `lecture` ; un seul écrivain ; départ de l’écrivain → le plus ancien prend la main.
- **pytest, CLI / instance** : `auth claude` trouve un faux `claude` sous `~orchestrator/.local/bin` avec un PATH de root minimal, et `runuser` sous `/usr/sbin` ; `KO` clair sans CLI. Compose construit depuis le ref du `direct_url.json` du paquet (commit, sinon `requested_revision`, sinon défaut). `setup` crée le lien, refuse d’écraser un fichier étranger ; `uninstall` le retire.
- **Vitest** : quitter la page de session ferme le websocket ; bouton **Prendre la main** en lecture seule ; page d’une session enchaînée qui suit la suivante ; chaîne dans la liste des sessions.
- Les suites des versions 0.1.0 à 0.4.0 restent vertes.
- Vraie instance installée avec `WAP_REF`, `sudo wap-runtime auth claude`, sessions Claude Code et Cursor avec skills, prise de main, enchaînement réel (avec le pack à jour sur `main`) : ticket de tests humains.

## Hors périmètre

- Session libre par repo, retrait du bouton `/implement #n` par ticket, catalogue d’actions : 0.4.2.
- Initialiser le pack dans un clone qui ne suit pas `agents/skills/`.
- Modifier `enchainer-implement.sh` / `encadrer-implement` sur cette branche (bug séparé sur `main`).
- Contenu des skills du pack ; assistant de premier lancement de Claude Code.
- Plusieurs écrivains simultanés ; plusieurs sessions ouvertes à la fois.
