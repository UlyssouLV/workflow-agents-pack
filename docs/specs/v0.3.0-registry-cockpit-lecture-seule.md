# V0.3.0 — Registry + cockpit lecture seule

## Problème

Après la 0.2.0, l’orchestrateur tourne sur la machine hôte mais ne sait rien des repos métier de l’utilisateur : aucun moyen de déclarer quels dépôts il suit, aucune connexion à GitHub (`gh` est installé sans authentification), et le seul service HTTP n’expose que `GET /health`. Pour savoir où en est chaque repo (version ouverte, tickets restants, tests humains à jouer, question en attente, CI rouge), l’utilisateur doit ouvrir GitHub repo par repo et reconstituer le cycle du pack de tête.

## Solution

L’utilisateur **déclare ses repos liés** (`owner/name`) par la CLI, **connecte l’orchestrateur à GitHub** une fois (commande réutilisable après une déconnexion), puis ouvre un **cockpit local en lecture seule**, servi par son instance sur `127.0.0.1` (tunnel SSH hors de l’hôte).

Le cockpit montre, pour chaque repo, la version ouverte, sa progression, et **une étape** déduite du tracker (labels, sub-issues, checks de la PR), avec un badge **Intervention humaine requise** quand l’étape attend quelqu’un. Une vue détail par repo montre tous les signaux, lus en direct. Aucun bouton d’action : les liens ouvrent GitHub.

```bash
sudo wap-runtime auth                       # device flow GitHub, réutilisable
sudo wap-runtime repo add mon-org/mon-repo
ssh -L 8787:127.0.0.1:8787 mon-serveur      # puis http://127.0.0.1:8787/
```

## User stories

1. En tant qu’utilisateur, je déclare un repo métier avec `sudo wap-runtime repo add owner/name` ; je rafraîchis le cockpit et il apparaît, sans redémarrage.
2. En tant qu’utilisateur, `repo list` me montre mes repos liés et `repo remove` en retire un ; un `owner/name` invalide ou en double est refusé avec un message clair.
3. En tant qu’utilisateur qui lance l’installation dans un terminal, le setup enchaîne sur la connexion GitHub (code + URL à valider dans mon navigateur).
4. En tant qu’utilisateur d’une installation automatisée (sans terminal, ou `WAP_SKIP_AUTH=1`), le setup ne bloque pas et m’indique la prochaine étape : `sudo wap-runtime auth`. Avec `GH_TOKEN` dans l’environnement, il l’utilise sans interaction.
5. En tant qu’utilisateur déconnecté (token révoqué ou expiré), je relance `sudo wap-runtime auth` et tout refonctionne ; `--with-token` me permet de fournir un token fine-grained sur stdin ; `auth status` me dit si l’orchestrateur est connecté et sous quel compte.
6. En tant qu’utilisateur, la vue liste du cockpit me montre une ligne par repo : nom, version ouverte, progression X/Y, étape, badge intervention humaine, heure de lecture ; les repos qui m’attendent sont en tête.
7. En tant qu’utilisateur, j’ouvre la vue d’un repo et à chaque rafraîchissement je vois son dernier état : parent, enfants (état, labels, bloqué ou non), PR de version et ses checks, bugs ouverts.
8. En tant qu’utilisateur, si un repo est inaccessible (introuvable, token sans droit, limite d’appels), seule sa ligne est en erreur, avec un message actionnable ; les autres s’affichent.
9. En tant qu’utilisateur non connecté à GitHub (ou dont le token est refusé), un bandeau me dit de lancer `sudo wap-runtime auth`.
10. En tant qu’utilisateur, je vois tout de suite qu’un repo attend une réponse (`needs-info`), des tests humains, une code review / Finalise ou une correction de CI.

## Étapes affichées

Une seule étape par version ouverte, la première qui s’applique dans cet ordre :

| # | Étape | Règle | Humain requis |
| --- | --- | --- | --- |
| 1 | Question en attente | un enfant ouvert porte `needs-info` | oui |
| 2 | CI en échec | checks / statuts du dernier commit de la PR de version : échec | oui |
| 3 | Tests humains en cours | un enfant ouvert porte `in-human-test` (en pratique l’enfant « Tests humains ») | oui |
| 4 | Tests humains à faire | tous les enfants ouverts portent `ready-for-human` (en pratique, seul l’enfant « Tests humains » reste ouvert) | oui |
| 5 | Tests agent en cours | un enfant ouvert porte `in-agent-test` | non |
| 6 | CI en cours | checks / statuts du dernier commit de la PR : en attente | non |
| 7 | Implement | au moins un enfant `ready-for-agent` ouvert | non |
| 8 | Code review / Finalise à faire | tous les enfants fermés, PR ouverte | oui |
| 9 | Pas de version ouverte | aucun parent ouvert | — |
| — | Étape indéterminée | aucune règle ne s’applique (ex. enfants tous fermés sans PR de version, ou enfants ouverts sans label déclencheur) | non |

Étape d’un **repo** (vue liste) : parmi celles de ses versions, une étape qui attend quelqu’un l’emporte, puis le plus petit numéro ; le badge suit cette étape. La vue détail montre l’étape et tous les signaux de chaque version.

Le cockpit **lit** ces labels ; il ne les pose pas. Faire poser / retirer `needs-info`, `in-agent-test` et `in-human-test` par les skills du pack est un chantier du pack, hors de cette version.

## Décisions d’implémentation

- **Repo lié** : `owner/name` GitHub, nom d’affichage facultatif ; aucun clone (les clones gérés par l’hôte arrivent avec le runner).
- **Registry** : `~/.wap-runtime/repos.toml` de l’instance, séparé de `config.toml` ; `setup` ne le crée ni ne le réécrit (absent = registry vide, cockpit vide avec un message d’aide). Éditable à la main.
- **CLI** `wap-runtime repo add|remove|list` : valide `owner/name`, refuse les doublons. Lancée en root (`sudo`), elle vise l’instance de l’utilisateur d’instance (même règle que `health`).
- **Compose** : monte le dossier de l’instance **en lecture seule** sur `/instance` (pas `repos.toml` seul : un bind mount d’un fichier absent crée un dossier sur l’hôte, et le remplacement atomique du fichier casserait le montage) ; le runtime relit `repos.toml` à chaque requête. Le conteneur reçoit déjà `secrets.env` par `env_file` ; il voit aussi `config.toml`, sans pouvoir rien écrire.
- **Authentification** `wap-runtime auth` :
  - lance `gh auth login` (device flow) **en tant qu’utilisateur d’instance** sur l’hôte ;
  - copie le token (`gh auth token`) dans `secrets.env` (`0600`) sous `GH_TOKEN`, puis redémarre le service `runtime` (un `env_file` n’est lu qu’au démarrage) ;
  - `--with-token` lit un token sur stdin ; `auth status` affiche l’état et le compte ;
  - idempotente, à relancer après une déconnexion.
  Le même `gh` authentifié servira au runner (0.4.0).
- **Setup** : en fin de passe, si l’orchestrateur n’est pas connecté — `GH_TOKEN` présent dans l’environnement → utilisé sans interaction ; sinon terminal disponible (`/dev/tty`) et pas `WAP_SKIP_AUTH=1` → enchaîne sur `auth` ; sinon affiche « prochaine étape : `sudo wap-runtime auth` ». Seule l’auth peut interagir (ADR 0003).
- **Lecture GitHub** : client HTTP Python (`httpx`) vers l’API REST GitHub avec `GH_TOKEN` ; URL de base injectable (tests). Pas de `gh` dans l’image.
  - Version ouverte = issue ouverte du repo ayant des sub-issues ; plusieurs → toutes affichées.
  - Progression = `sub_issues_summary` (`completed` / `total`).
  - PR de version = PR ouverte dont le corps contient `Fixes #<parent>` ; checks / statuts de son commit de tête.
  - Bugs = issues ouvertes label `bug`.
- **Fraîcheur** : vue liste derrière un cache mémoire de 60 s (heure de lecture affichée, rafraîchissement automatique de la page à 60 s) ; vue détail lue en direct, sans cache. Rien n’est persisté.
- **Backend** : **FastAPI** (servi par uvicorn) remplace le serveur stdlib : `GET /health` (contrat inchangé : `{"status": "ok", "version": …}`), API JSON sous `/api/` (liste, détail d’un repo, état d’auth), fichiers du front servis sur `/`.
- **Front** : **React + TypeScript + Vite** dans `orchestrator/cockpit/`, style minimal. Deux vues : liste `/` (repos « humain requis » en tête) et détail `/repos/<owner>/<name>`. Liens vers GitHub, aucune action.
- **Image** : Dockerfile multi-étapes ; une étape Node construit le front, les fichiers statiques sont copiés dans l’image Python. Pas de Node sur l’hôte. Dépendances Python épinglées par hash comme en 0.2.0.
- **Erreurs** : par repo (404, 401/403, limite d’appels) avec un message court ; bandeau global si non connecté, token refusé ou GitHub injoignable. Connecté, le cockpit affiche le compte GitHub.
- **Accès** : port publié sur `127.0.0.1` uniquement (ADR 0002) ; tunnel SSH documenté dans le README.
- **Rien de global à la machine** : registry, token, cache propres à l’instance (`~/.wap-runtime/` de l’utilisateur d’instance) ; aucun nouveau chemin système ni port codé en dur (prépare les instances multiples).
- **Version** du paquet : `0.3.0`.
- **Docs** : ADR 0003 (auth GitHub interactive dans le setup quand un terminal existe) ; glossaire (*registry*, *repo lié*, *étape*, *intervention humaine*) ; README (auth, registry, cockpit, tunnel SSH).

## Décisions de test

- **Deux test-roots** : `orchestrator/` (pytest) et `orchestrator/cockpit/` (Vitest via `npm test`).
- **pytest, frontière HTTP** : application FastAPI testée en process contre un **faux GitHub** (serveur local ou transport `httpx` injecté) :
  - chaque étape du tableau, et la priorité quand plusieurs règles s’appliquent ;
  - progression, plusieurs versions ouvertes, PR liée par `Fixes`, bugs ;
  - erreur d’un repo n’empêche pas les autres ; bandeau sans token / token refusé ;
  - cache de 60 s sur la liste (horloge injectée), détail toujours relu ;
  - `/health` inchangé.
- **pytest, CLI** : `repo add/remove/list` sur un `HOME` temporaire (validation, doublons, root → instance) ; `auth` avec un faux `gh` dans le `PATH` (token copié dans `secrets.env` en `0600`, redémarrage demandé, `--with-token`, `status`) ; enchaînement du setup (`GH_TOKEN`, terminal, `WAP_SKIP_AUTH`).
- **pytest, instance** : `compose.yaml` monte l’instance (donc `repos.toml`) en lecture seule ; `setup` ne touche pas `repos.toml`.
- **Vitest** : rendu des deux vues à partir de réponses `/api/` simulées (tri humain requis en tête, badge, erreur par ligne, bandeau d’auth).
- Les suites de la 0.1.0 et de la 0.2.0 restent vertes.
- Le vrai device flow, le cockpit par tunnel SSH et des repos réels : ticket de tests humains.

## Hors périmètre

- Toute action agent depuis le cockpit (`/implement`, boutons, formulaires).
- Le vrai design du cockpit (style minimal seulement).
- Modifier les skills du pack pour poser / retirer `needs-info`, `in-agent-test`, `in-human-test` (signalé par une issue séparée).
- Labels déclencheurs configurables par instance.
- Clones locaux des repos liés, runner.
- Instances multiples sur un même hôte, accès web authentifié, exposition hors `127.0.0.1`.
- Webhooks GitHub, relevé en tâche de fond, persistance de l’état.
