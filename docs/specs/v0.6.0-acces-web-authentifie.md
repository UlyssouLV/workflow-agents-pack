# V0.6.0 — Accès web authentifié

Parent : [#89](https://github.com/UlyssouLV/workflow-agents-pack/issues/89)

## Problème

Depuis la 0.3.0, le cockpit est joignable dès qu’on atteint le port du service `runtime` (HTTP clair sur `127.0.0.1`, sans login). L’accès distant documenté passe par un tunnel SSH. Pour joindre le cockpit depuis Internet de façon sûre — authentification propre à l’instance, aucun service runtime exposé en clair, chemin reverse proxy vers une machine du réseau privé sans ouvrir le reste du LAN — il manque une porte d’entrée authentifiée, un reverse proxy livré avec le produit, et une doc qui couvre tous les cas (local, SSH, expo publique, domaine / pas de domaine, box / NAT).

## Solution

Un jeu d’identifiants **par instance** (login + mot de passe), distinct de `wap-runtime auth` (GitHub / agents). Auth **obligatoire** pour tout accès au cockpit (y compris local). Sessions serveur (cookie httpOnly + stockage dans l’instance). **Caddy** conteneurisé dans Compose, **opt-in** (activable / désactivable) : quand l’exposition est on, seuls 80/443 du proxy sont publiés ; `runtime` et `runner` restent hors Internet. HTTPS Let’s Encrypt dès qu’un nom de domaine pointe vers la machine ; pas de mode officiel « HTTP public ». Doc README refondue (sujet de la branche, install, config, tous les cas d’accès) + checklist DNS/NAT + commande de diagnostic. Tunnel SSH conservé. Tests anti-échappement : rien de servi ne doit permettre d’atteindre autre chose que le cockpit via le proxy.

## User stories

1. En tant qu’opérateur, je veux un login et un mot de passe pour mon instance, pour que seul quelqu’un qui les connaît ouvre le cockpit.
2. En tant qu’opérateur, je veux que ces identifiants soient distincts des tokens GitHub et agents, pour que l’accès web ne soit pas `wap-runtime auth`.
3. En tant qu’opérateur, je veux une commande CLI pour créer les identifiants cockpit avant le premier usage, pour que le cockpit ne soit jamais joignable sans mot de passe configuré.
4. En tant qu’opérateur, je veux une commande CLI pour changer le mot de passe après déploiement, pour pouvoir le faire tourner sans réinstaller.
5. En tant qu’opérateur, quand je change le mot de passe, je veux que les sessions ouvertes soient invalidées, pour qu’un cookie volé ne garde pas l’accès.
6. En tant qu’opérateur, je veux que toute page et API du cockpit (sauf la surface de login et un health sans secrets) exige une session, y compris sur `127.0.0.1`, pour qu’un proxy mal configuré ne contourne pas l’auth en frappant localhost.
7. En tant qu’opérateur, je veux me connecter via une page de login et rester authentifié avec une session navigateur sûre (cookie httpOnly, stockage serveur), pour ne pas retaper le mot de passe à chaque clic.
8. En tant qu’opérateur, je veux une déconnexion explicite, pour couper la session sur un navigateur partagé.
9. En tant qu’opérateur, je veux que les tentatives de login échouées soient limitées / verrouillées temporairement, pour ralentir le brute-force.
10. En tant qu’opérateur, je veux une durée de session de l’ordre de plusieurs jours (~7) sauf déconnexion ou rotation du mot de passe, pour un usage quotidien confortable.
11. En tant qu’opérateur, je veux un reverse proxy Caddy livré dans Compose avec cette version, pour ne pas inventer seul l’entrée publique.
12. En tant qu’opérateur, je veux que l’exposition web (Caddy / ports 80–443) soit opt-in et désactivable à la demande, pour pouvoir rester en local uniquement.
13. En tant qu’opérateur, quand l’exposition est on, je veux que seuls les ports du reverse proxy soient publiés sur l’hôte, pour que `runtime` et `runner` ne soient pas joignables depuis Internet.
14. En tant qu’opérateur, je veux que le proxy ne relaie que vers le cockpit de cette instance, pour que le chemin n’ouvre pas le reste du réseau privé.
15. En tant qu’opérateur sans nom de domaine encore, je veux continuer l’accès local ou le tunnel SSH avec auth, pour ne pas être poussé vers du HTTP clair sur Internet.
16. En tant qu’opérateur avec un nom de domaine qui pointe vers ma machine (et un NAT qui marche si box maison), je veux que Caddy obtienne et renouvelle des certificats Let’s Encrypt, pour un accès public en HTTPS.
17. En tant qu’opérateur, je ne veux pas de mode officiel « HTTP public », pour ne pas envoyer le mot de passe en clair sur Internet.
18. En tant qu’opérateur, je veux un README qui explique le sujet de cette branche (orchestrateur vs pack sur `main`), l’install, la config, et tous les cas d’accès (local, SSH, expo off/on, sans domaine, domaine + DNS + NAT, CGNAT possible, diagnostic), pour que le README soit une vraie porte d’entrée.
19. En tant qu’opérateur, je veux une CLI de diagnostic (Caddy up, ports, auth cockpit configurée, reste DNS/NAT), pour savoir ce que le produit a fait vs ce que ma box doit faire.
20. En tant qu’opérateur, je veux que le tunnel SSH documenté reste valide, pour joindre le cockpit sans ouvrir la box.
21. En tant qu’opérateur, je veux des tests automatiques que la surface proxifiée ne permet pas d’échapper vers d’autres hôtes ou services, pour que « absolument sûr pour le réseau privé » soit vérifié.
22. En tant que développeur de l’orchestrateur, je veux glossaire et ADR à jour pour le vocabulaire et les décisions dures, pour les versions suivantes.

## Décisions d’implémentation

- **Vocabulaire** : distinguer **identifiants cockpit** (accès web à l’instance) de **auth GitHub / agents** (`wap-runtime auth*`). Exposition web = reverse proxy Caddy **opt-in**.
- **Identifiants** : un seul jeu login + mot de passe par instance ; hash stocké dans l’instance (pas en clair) ; CLI de création et de changement après déploiement.
- **Sessions** : cookie httpOnly + sessions côté serveur dans l’instance (SQLite ou fichier équivalent sous `~/.wap-runtime/`) ; déconnexion et changement de mot de passe invalident ; durée ~7 jours ; limitation des tentatives de login.
- **Garde HTTP** : toute route cockpit/API exige une session valide, sauf page de login (+ assets nécessaires) et `GET /health` sans secrets métier. Auth aussi sur accès loopback.
- **Caddy** : service Compose livré dans 0.6.0 ; écoute 80/443 quand l’expo est activée ; relaie uniquement vers le service cockpit de l’instance ; `runtime` reste non publié sur Internet.
- **TLS** : Let’s Encrypt via Caddy lorsqu’un nom de domaine pointe vers la machine ; pas de mode officiel HTTP public ; sans domaine, usage local / SSH avec auth ; certificat fourni ou auto-signé seulement comme lab documenté avec avertissement si besoin.
- **Réseau utilisateur** : DNS et redirection de ports (NAT sur la box) restent côté opérateur ; Caddy tourne sur la **machine hôte**, pas sur la box ; documenter CGNAT (ex. box 4G) comme limite possible.
- **CLI** : activer / désactiver l’exposition ; diagnostic (Caddy, ports, auth cockpit configurée, reste DNS/NAT).
- **README** : refonte — sujet de la branche `feat/runtime-orchestrator` (vs pack sur `main`), méthodes d’installation, configuration, tous les cas d’accès ci-dessus ; trajectoire alignée sur la feuille de route actuelle.
- **ADR** : 0010 (identifiants cockpit + auth partout) ; 0011 (Caddy opt-in borné au cockpit).
- **Version** du paquet : `0.6.0`.

## Décisions de test

- Bon test = comportement observable aux coutures (HTTP, CLI, Compose), pas l’intérieur de Caddy ni le détail du hash.
- **Couture principale** : bord HTTP du service `runtime` — login / logout / session ; refus sans session ; `/health` sans secrets.
- **pytest, CLI / instance** : bootstrap et changement de mot de passe ; invalidation des sessions ; expo on/off ; diagnostic.
- **pytest / fixtures Compose** : Caddy présent si expo on ; seuls 80/443 publiés côté proxy ; runtime non exposé Internet.
- **Anti-échappement** : la config / surface servie ne permet pas de relayer hors du cockpit de l’instance.
- **Vitest** : page de login, redirection si non authentifié, déconnexion.
- Suites 0.1.0–0.5.1 restent vertes.
- Tests humains : login local ; changer le mot de passe ; expo off ; doc des cas ; (si domaine/NAT dispo) HTTPS via Caddy.

## Hors périmètre

- Instances multiples isolées sur le même serveur.
- SaaS multi-tenant ; comptes partagés entre instances ; plusieurs opérateurs avec comptes distincts sur une même instance.
- Tunnel produit type Cloudflare / Tailscale comme mécanisme d’exposition (le chemin retenu est Caddy + DNS/NAT opérateur).
- Configuration automatique de la box / du routeur.
- Facturation ; enregistrement self-service par compte GitHub (0.8.0).
- Refonte graphique du cockpit (0.8.1) au-delà de la page de login nécessaire.
- Chantier labels d’état du pack (#24) ; bug `/afr` (#80) sauf s’il est explicitement traité ailleurs.

## Notes

- Sans nom de domaine au jour J : livrable quand même (auth + Caddy opt-in + doc) ; HTTPS public Let’s Encrypt dès que le domaine et le NAT le permettent.
- La box (ex. Bouygues 4G) ne reçoit pas Caddy ; elle peut seulement forwarder les ports si le réseau le permet.
