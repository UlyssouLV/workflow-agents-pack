# V0.4.2 — Session libre et réponse attendue

## Problème

Depuis la 0.4.0, le cockpit ne lance qu’une chose : `/implement #n` sur un enfant éligible, sur la branche de la PR de version. Le reste du cycle (« Ouvre la version », `/th`, `/code-review`, « Finalise la version », `/cqg`…) exige encore un poste local. Une seule session peut être ouverte sur toute l’instance, et le cockpit ne sait que si elle est ouverte ou fermée : quand l’agent attend une réponse (grilling, question, validation), rien ne le signale, et l’humain ne peut pas lancer une session sur un autre repo pendant ce temps.

## Solution

Depuis la vue détail d’un repo, l’utilisateur choisit l’agent et la branche, puis clique **Nouvelle session** : l’agent démarre **vide** dans le terminal, et l’humain y tape ce qu’il veut (`/implement #n`, « Ouvre la version », `/th`…), exactement comme en local. Les boutons `/implement #n` par ticket disparaissent.

Plusieurs sessions peuvent être ouvertes, **une par repo**. Chaque session ouverte montre son **activité** — *travaille*, *réponse attendue* (avec le dernier skill chargé, ex. « réponse attendue — grilling ») ou *inconnue* — remontée par des hooks des agents. Une nouvelle page **Sessions** liste toutes les sessions de l’instance ; l’en-tête et le titre de l’onglet comptent les réponses attendues.

## User stories

1. En tant qu’utilisateur, sur la vue détail d’un repo, je choisis l’agent et la branche (base d’intégration ou branche d’une PR de version ouverte ; par défaut la PR de version s’il y en a une, sinon la base) et je clique **Nouvelle session** : l’agent démarre sans commande dans le clone géré, sur cette branche, et je tape ce que je veux.
2. En tant qu’utilisateur, je lance « Ouvre la version » depuis une session sur la base d’un repo qui n’a pas encore de PR de version.
3. En tant qu’utilisateur, je ne vois plus de bouton `/implement #n` par ticket ; les tickets restent affichés.
4. En tant qu’utilisateur, le bouton **Nouvelle session** grisé me dit pourquoi : agent non connecté, session déjà ouverte sur ce repo (avec le lien), ou une session travaille sur un autre repo (avec le lien).
5. En tant qu’utilisateur, pendant qu’une session attend ma réponse sur un repo, je lance une session sur un autre repo.
6. En tant qu’utilisateur, je vois si une session ouverte **travaille**, attend une **réponse** (et quel skill tourne quand c’est connu, ex. « réponse attendue — grilling »), ou si son activité est **inconnue** (agent sans hooks).
7. En tant qu’utilisateur, je réponds à une session en attente même si une autre travaille : le terminal n’est jamais bloqué par l’activité d’une autre session.
8. En tant qu’utilisateur, la page **Sessions** liste toutes les sessions de l’instance (plus récentes d’abord) : repo, agent, branche, titre, état, activité ; un clic ouvre la session.
9. En tant qu’utilisateur, le titre d’une session est le premier message que j’y ai tapé (sinon le nom de l’agent).
10. En tant qu’utilisateur, la vue liste montre **Travaille** ou **Réponse attendue** sur chaque repo qui a une session ouverte ; l’en-tête affiche « N réponse(s) attendue(s) » (lien vers Sessions) et le titre de l’onglet `(N) …`.
11. En tant qu’utilisateur, si le clone est sale, la boîte de dialogue me dit sur quelle branche il est et combien de fichiers sont modifiés : **Reprendre** lance sur cette branche telle quelle, **Jeter** nettoie puis passe sur la branche choisie.
12. En tant qu’utilisateur, quand je tape `/implement #n` dans une session libre et qu’`encadrer-implement` enchaîne, la session suivante `/implement #m` démarre comme en 0.4.1.

## Décisions d’implémentation

- **Lancement** : `POST /api/sessions` prend `repo`, `agent`, `branche`, et le choix Reprendre / Jeter si demandé ; plus de `ticket`. L’agent démarre en mode interactif **sans argument** (`claude`, `agent`). `session.json` : `ticket` vaut `null` pour une session libre (une session enchaînée garde son ticket), nouveau champ `branche`.
- **Branches proposées** : la base d’intégration (`base_branch` de `agents/integration-channel.yml` lu dans le repo sur GitHub, sinon la branche par défaut du repo) et la branche de chaque PR de version ouverte. Le runner refuse toute autre branche. Une session sur la base n’exige pas de PR.
- **Plusieurs sessions ouvertes** :
  - au plus **une session ouverte par repo** (clone géré unique) ; deuxième lancement sur le même repo → `409` avec le lien ;
  - lancement refusé (`409`, lien) tant qu’une session d’un autre repo a l’activité *travaille* ; *inconnue* et *réponse attendue* ne bloquent pas ;
  - aucun blocage du clavier selon l’activité des autres sessions ;
  - au redémarrage du runner, toutes les sessions ouvertes passent `interrompue` (comme en 0.4.0).
- **Activité** (session ouverte seulement) : `travaille`, `attend` (+ `skill` optionnel), `inconnue` (valeur de départ). Stockée dans `session.json`.
  - Le runner installe des **hooks en portée utilisateur** dans `runner-home` (fusionnés avec les réglages existants, aucun fichier suivi du clone touché) qui appellent `wap-runtime etat <travaille|attend> [--skill <nom>]` ; la commande passe par l’API interne du runner avec `WAP_SESSION` et `WAP_SESSION_JETON` (jeton de la session ouverte, réutilisable, distinct de l’usage unique de l’enchaînement côté contrôle).
  - Claude Code : soumission d’un message → `travaille` ; `Stop` et `Notification` (attente de permission ou d’entrée) → `attend` ; appel de l’outil `Skill` → retient le nom du skill. Le premier message soumis devient le `titre` de la session.
  - Cursor : mêmes hooks si la CLI épinglée les expose (à vérifier en implémentation) ; sinon l’activité reste `inconnue` et le titre reste le nom de l’agent.
  - Une erreur de hook ne bloque jamais l’agent (le hook rend 0).
- **Enchaînement (ADR 0006)** : permis depuis toute session ouverte sur la branche d’une PR de version, libre ou non ; mêmes règles qu’en 0.4.1 ; la suivante est une session `/implement #m` (agent lancé sur cette commande). La règle « une session par repo » ne s’y oppose pas (la courante se ferme). Elle n’est pas soumise à la règle « une autre session travaille ».
- **Clone sale** : `CloneSale` renvoie aussi la branche actuelle du clone. **Reprendre** = branche actuelle, sans changement ; **Jeter** = patch enregistré, `reset --hard` + `clean -fd`, puis branche choisie.
- **API** : `GET /api/sessions` (toutes les sessions, plus récentes d’abord, avec activité) ; les réponses existantes (repo, sessions d’un repo, session) portent `activite`, `skill`, `titre`, `branche`.
- **Cockpit** :
  - vue détail : sélecteur d’agent, sélecteur de branche, bouton **Nouvelle session** (grisé + raison) ; plus de boutons par ticket ;
  - nouvelle page **`/sessions`** ; lien dans l’en-tête ;
  - vue liste : badge **Travaille** / **Réponse attendue** (activité *inconnue* → **Session en cours**) ;
  - en-tête : « N réponse(s) attendue(s) » ; titre de l’onglet `(N) …` quand N > 0 ;
  - page de session : activité affichée ; titre ;
  - rafraîchissement par le relevé périodique existant.
- **Version** du paquet : `0.4.2`.
- **Docs** : ADR 0007 (plusieurs sessions ouvertes, une par repo ; activité par hooks en portée utilisateur ; remplace le point 4 de l’ADR 0004) ; glossaire (*Session libre*, *Activité*, mise à jour de *Session*) ; README (session libre, activité, page Sessions).

## Décisions de test

- **pytest, runner** (clone local, fausse CLI agent, faux tmux) : session libre lancée sans argument sur la branche choisie ; base acceptée sans PR ; branche inconnue refusée ; deuxième session sur le même repo → refus ; session d’un autre repo qui *travaille* → refus, *attend* / *inconnue* → accepté ; clone sale : branche actuelle rendue, Reprendre sans changement de branche, Jeter puis branche choisie.
- **pytest, activité** : `wap-runtime etat` avec le bon jeton met à jour l’activité, le skill et le titre (premier message seulement) ; mauvais jeton ou session close → refus, le hook rend quand même 0 ; hooks écrits dans `runner-home` en conservant les réglages existants ; enchaînement depuis une session libre sur la branche de PR.
- **pytest, HTTP** : `POST /api/sessions` sans ticket ; `409` avec lien dans les deux cas de refus ; `GET /api/sessions` ; champs `activite` / `skill` / `titre` / `branche` dans les réponses.
- **Vitest** : sélecteurs et bouton **Nouvelle session** (raisons de grisé) ; absence de boutons par ticket ; page Sessions ; badges de la vue liste ; compteur d’en-tête et titre de l’onglet ; boîte de dialogue du clone sale avec la branche.
- Les suites des versions 0.1.0 à 0.4.1 restent vertes (adaptées au retrait du bouton par ticket).
- Vraies sessions Claude Code et Cursor, « Ouvre la version » sur la base, réponse attendue pendant un grilling, deux repos ouverts : ticket de tests humains.

## Hors périmètre

- Catalogue de boutons par étape du workflow.
- Plusieurs sessions sur le même repo (worktrees) : *Plus tard*, « Plusieurs sessions ouvertes ».
- Reprendre une conversation passée (`--resume`).
- Notifications du navigateur et alertes à l’humain : 0.5.0.
- Garantie stricte « une seule session travaille » (blocage du clavier).
- Autopilot (0.5.0) : l’enchaînement reste décidé par le skill dans la session.
