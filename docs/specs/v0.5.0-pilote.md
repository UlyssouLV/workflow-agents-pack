# V0.5.0 — Pilote (autopilot borné)

## Problème

Depuis la 0.4.1 / 0.4.2, une chaîne Implement peut déjà avancer sans humain **une fois démarrée** : `encadrer-implement` (pack) enchaîne via `wap-runtime enchainer` (ADR 0006), et le cockpit montre l’activité des sessions (ADR 0007). Mais le **premier** `/implement #n` et la **reprise** après un stop (grilling, besoin humain, erreur) exigent encore quelqu’un devant le cockpit. Sans onglet ouvert, personne n’est alerté. Le « bornage » de la chaîne n’est pas un trou runtime : il est déjà le job des skills du pack ; ce qui manque est un **rôle de surveillance** qui démarre, observe et notifie.

## Solution

Sur chaque repo lié, un interrupteur **Pilote** (opt-in) + agent préféré. Une boucle dans le service `runtime` (navigateur fermé OK) démarre le premier enfant Implement éligible, laisse le pack enchaîner, surveille activité / étapes / état de session, s’arrête et envoie une **notification navigateur** dès qu’un humain doit agir, puis reprend automatiquement tant que le toggle reste ON. Le runtime ne choisit pas la politique d’enchaînement : il ne relance que s’il n’y a **pas** de session ouverte et qu’un enfant est éligible.

## User stories

1. En tant qu’utilisateur, sur la vue détail d’un repo lié, j’active **Pilote** et je choisis l’agent préféré (Claude ou Cursor), pour que ce repo soit gardé sous surveillance sans que j’aie à relancer chaque ticket.
2. En tant qu’utilisateur, mon choix (toggle + agent) survit au redémarrage du service `runtime` (persisté dans le registry du repo).
3. En tant qu’utilisateur, dès que le pilote est ON et qu’un enfant `ready-for-agent` non bloqué existe sur une version avec PR, le runtime lance `/implement #n` sans que j’ouvre le cockpit.
4. En tant qu’utilisateur, s’il y a plusieurs enfants éligibles en parallèle, le pilote prend le plus petit numéro d’issue (ordre d’implémentation de la version via Blocked by déjà respecté par l’éligibilité).
5. En tant qu’utilisateur, le lancement auto se fait sur la branche de la PR de version (pas sur la base, pas de session libre « Ouvre la version »).
6. En tant qu’utilisateur, si le clone est sale, le pilote ne lance pas et me notifie : je décide Reprendre / Jeter comme en 0.4.2.
7. En tant qu’utilisateur, pendant qu’`encadrer-implement` enchaîne, le pilote ne double pas le lancement : il surveille seulement tant qu’une session est ouverte sur ce repo.
8. En tant qu’utilisateur, je peux quand même ouvrir une **Nouvelle session** libre sur un repo sous pilote ; tant qu’elle est ouverte, le pilote ne lance pas ; à la fermeture il reprend s’il reste un enfant éligible.
9. En tant qu’utilisateur, si je coupe **Pilote** pendant une session en cours, la session continue ; le pilote ne relancera plus ensuite.
10. En tant qu’utilisateur, quand une session sous pilote passe en activité *réponse attendue*, je reçois une notification navigateur, la session reste ouverte pour que je réponde, et le pilote ne lance pas une autre session sur ce repo.
11. En tant qu’utilisateur, quand l’étape du repo devient *intervention humaine* (question, CI en échec, tests humains, Finalise…), ou qu’il n’y a plus d’enfant éligible, ou qu’une session est *échouée* / *interrompue*, ou qu’un lancement échoue (agent down…), je suis notifié et le pilote ne relance pas tant que la condition dure.
12. En tant qu’utilisateur, après avoir débloqué la situation (réponse, correction CI, etc.), le pilote reprend tout seul s’il reste ON et qu’un enfant redevient éligible.
13. En tant qu’utilisateur, plusieurs repos peuvent être sous pilote ; une seule session *travaille* à la fois sur l’instance (règles 0.4.2) ; les autres attendent leur tour.
14. En tant qu’utilisateur, la vue liste montre quels repos sont sous pilote (et s’ils sont en pause / stop : attend, humain requis…).
15. En tant qu’utilisateur, avec le cockpit ouvert j’autorise les notifications navigateur une fois ; ensuite chaque stop me prévient même si je regarde un autre onglet.
16. En tant qu’utilisateur, je n’attends pas du pilote qu’il lance « Ouvre la version », `/th`, `/code-review`, « Finalise » ou `/cqg` — seulement l’Implement sous surveillance.

## Décisions d’implémentation

- **Vocabulaire** : concept produit = **Pilote** (toggle, badge). Titre de version / feuille de route peut garder « Autopilot borné » ; le bornage de la chaîne = skills du pack (`encadrer-implement`), pas une politique runtime qui redécide le prochain ticket.
- **Persistance** : champs par `[[repos]]` dans `repos.toml` (ex. `pilote = true`, `agent = "claude"` | `"agent"`). Éditables à la main comme le reste du registry.
- **Boucle** : dans le service `runtime` (pas dans le navigateur, pas de 3ᵉ conteneur). Elle lit registry + détail GitHub / sessions déjà exposés par le cockpit, décide lancer / attendre / stopper+signaler.
- **Lancement** : réutilise les règles d’éligibilité existantes (`ready-for-agent`, non bloqué, PR de version, pas de session ouverte, agent connecté). Branche = celle de la PR. Crée une session libre puis envoie `/implement #n` comme **premier message** dans le terminal. L’enchaînement (ADR 0006) garde le chemin CLI / `enchainer` inchangé.
- **Choix de `#n`** : parmi les éligibles, plus petit numéro d’issue.
- **Non-lancement** si session déjà ouverte sur le repo (y compris chaîne en cours), clone sale, agent préféré non connecté, pas de PR de version, ou stop actif (ci-dessous).
- **Stops** (notif + pas de nouveau lancement) : session `échouée` / `interrompue` ; activité `attend` ; étape `humain_requis` ; plus aucun enfant éligible ; échec de lancement. Sur `attend`, la session **reste ouverte**.
- **Reprise** : automatique tant que `pilote = true`, dès qu’il n’y a plus de session ouverte et qu’un enfant est à nouveau éligible (et aucun stop tracker bloquant le lancement).
- **Toggle OFF** : n’interrompt pas la session courante ; coupe seulement surveillance / relances.
- **API / cockpit** : lecture de l’état pilote sur liste et détail ; écriture toggle + agent (détail). Badge liste. Demandes de permission + `Notification` sur les stops (mockable en Vitest).
- **ADR** : une décision — boucle de surveillance dans `runtime` ; enchaînement inchangé (pack / ADR 0006).
- **Glossaire** : entrée **Pilote** ; préciser que le runtime ne remplace pas l’enchaînement du pack.
- **Version** du paquet : `0.5.0`.
- **Docs** : README (activer le pilote, notifs, limites).

## Décisions de test

- Couture principale : boucle pilote au bord HTTP / façade runtime (détail + sessions contrôlés), pas l’intérieur du timer de poll.
- **pytest, registry** : lire/écrire `pilote` + agent ; persistance sur disque.
- **pytest, boucle** : lance si ON + éligible + pas de session ; refuse si session ouverte / clone sale / `humain_requis` / agent down ; reprend après fermeture de session si encore éligible ; n’appelle pas `enchainer`.
- **pytest, HTTP** : champs pilote liste/détail ; activer/désactiver ; lancement = session puis premier message `/implement #n`.
- **Vitest** : toggle + sélecteur agent ; badge liste ; notifs sur stops (mock `Notification`).
- Suites 0.1.0–0.4.2 restent vertes.
- Tests humains : activer le pilote, premier lancement sans taper, enchaînement pack, stop sur `attend` + notif, reprise, toggle OFF sans tuer la session.

## Hors périmètre

- Automatiser « Ouvre la version », `/th`, `/code-review`, « Finalise la version », `/cqg`.
- Workers parallèles (plusieurs sessions *travaille* en même temps).
- Alertes hors navigateur (mail, webhook…).
- Poser / retirer `in-agent-test` / `in-human-test` (chantier pack [#24](https://github.com/UlyssouLV/workflow-agents-pack/issues/24)).
- Remplacer l’enchaînement du pack par une file runtime.
- SaaS multi-tenant, marketplace, orchestration hors machine utilisateur.
