# V0.7.1 — CD

Parent : [#106](https://github.com/UlyssouLV/workflow-agents-pack/issues/106)

## Problème

Depuis la 0.7.0, chaque PR vers `feat/runtime-orchestrator` est vérifiée par la CI, mais rien ne sort de cette validation. Les images `runtime` et `runner` sont construites **sur chaque hôte** au moment de `setup` (ADR 0005) : le digest qui tourne en production n’est pas celui qui a été testé, et un build long ou cassé sur l’hôte bloque l’installation. Une installation sans `WAP_REF` prend la **tête de la base**, pas une version livrée. Une fois installée, une instance ne se met jamais à jour seule : il faut relancer `install.sh` à la main sur chaque serveur. Après un reboot, les conteneurs repartent par `restart: unless-stopped` avec leurs anciennes images.

## Solution

Une **CD** sur le modèle d’ArgOS (0.7.2 — Livraison continue), adaptée au canal orchestrateur :

- **Images publiées** : `ghcr.io/ulyssoulv/wap-runtime` et `ghcr.io/ulyssoulv/wap-runner`, multi-arch `amd64` + `arm64`, paquets publics (tirables sans jeton).
- **Staging** : quand la CI d’une PR du dépôt vers la base est verte, un job `images` construit les deux images au **SHA de tête de la PR**, les pousse en `:sha-<sha>` et déplace `:staging`. Les tests humains tirent ces images.
- **Promotion** : la publication d’une Release `orchestrator-vX.Y.Z` (créée par Finalise sur le SHA de la branche de version) déclenche un workflow qui **retaggue le digest `:sha-<sha du tag>`** vers `X.Y.Z` et `latest`, sans rebuild : la production reçoit exactement ce qui a été testé.
- **Installation** : sans `WAP_REF`, `install.sh` installe la **dernière Release** (paquet pipx au tag, images `X.Y.Z` tirées de ghcr). Avec `WAP_REF=<ref>`, les images `:sha-<commit>` sont tirées si elles existent, sinon construites sur l’hôte (secours, ADR 0005).
- **Mise à jour de l’instance** : `sudo wap-runtime update` détecte une Release plus récente et l’applique (paquet, compose, pull, recreate) ; une unité systemd `wap-runtime.service`, calquée sur `argos.service`, lance cette mise à jour à chaque démarrage du serveur avant de relancer Compose.

Le README, un ADR 0013 et le glossaire ancrent ces choix. Le check `images` rejoint les checks requis de la ruleset.

## User stories

### Publication

1. En tant que mainteneur, je veux que la CI construise et pousse les images `runtime` et `runner` sur ghcr quand une PR vers la base est verte, pour qu’un digest testé existe avant la Release.
2. En tant que mainteneur, je veux ces images en `amd64` et `arm64`, pour que tout serveur Debian/Ubuntu supporté tire le même canal.
3. En tant que mainteneur, je veux que les images soient construites au SHA de tête de la PR (pas au merge-ref), pour que le tag de Release posé sur ce SHA retrouve son `:sha-<sha>`.
4. En tant que testeur humain, je veux une étiquette `:staging` qui suit la dernière PR verte, et `:sha-<sha>` pour un commit précis, pour tester la version avant Finalise.
5. En tant que mainteneur, je veux que les PR d’un fork ne publient rien, pour qu’aucun code non relu n’arrive sur ghcr.
6. En tant que mainteneur, je veux que le job `images` soit un check requis, pour qu’on ne puisse pas finaliser une version dont la promotion échouerait faute d’image.
7. En tant que responsable de release, je veux que la Release `orchestrator-vX.Y.Z` promeuve le digest `:sha-<sha>` vers `X.Y.Z` et `latest` sans rebuild, pour que la production reçoive exactement ce qui a été testé, sans geste supplémentaire.
8. En tant que responsable de release, je veux que la promotion échoue clairement si `:sha-<sha>` n’existe pas, pour ne jamais publier une version sans images.
9. En tant qu’adopteur, je veux tirer les images sans jeton (paquets publics), pour installer simplement.
10. En tant que mainteneur, je veux la doc du geste manuel unique qui rend les paquets ghcr publics, parce que l’API GitHub ne le permet pas.

### Installation

11. En tant qu’installateur, je veux que `install.sh` sans `WAP_REF` installe la dernière Release (paquet au tag, images `X.Y.Z`), pour ne plus installer une tête de branche par défaut.
12. En tant que développeur, je veux que `WAP_REF=<branche|commit>` tire `:sha-<commit>` s’il existe, pour tester une branche de version sans build sur l’hôte.
13. En tant que développeur, je veux qu’en l’absence d’image publiée (installation locale ou éditable, fork, commit jamais passé en CI) `setup` construise encore les images sur l’hôte, pour garder le chemin de l’ADR 0005.
14. En tant qu’administrateur, je veux que `config.toml` garde la version installée (`X.Y.Z` pour une Release, le ref sinon), pour savoir ce qui tourne.

### Mise à jour

15. En tant qu’administrateur, je veux une commande unique `sudo wap-runtime update` qui détecte et applique une Release plus récente, pour mettre à jour sans attendre un reboot.
16. En tant qu’administrateur, je veux des codes de sortie distincts (0 mise à jour faite, 2 rien à faire, 1 échec), pour scripter et lire le résultat.
17. En tant qu’administrateur, je veux qu’une instance installée depuis un ref non semver réponde « pas une version de production : rien à faire », pour qu’une instance de test ne bascule pas seule sur une Release.
18. En tant qu’administrateur, je veux que la mise à jour ne fasse rien tant que les images `X.Y.Z` ne sont pas sur ghcr, pour ne pas casser l’instance entre la Release et la fin de la promotion.
19. En tant qu’administrateur, je veux que `update` refuse quand une session est ouverte (sauf `--force`), parce que le recreate du `runner` interromprait l’agent.
20. En tant qu’administrateur, je veux que la mise à jour réinstalle le paquet au tag, régénère `compose.yaml`, tire les images et recrée les services, sans toucher à `config.toml`, aux secrets, à `repos.toml`, `jobs/` ni `clones/`.
21. En tant qu’administrateur, je veux qu’un échec soit journalisé sans rollback automatique, pour corriger à la main.
22. En tant qu’administrateur, je veux que seules les anciennes images `wap-runtime` / `wap-runner` soient supprimées après une mise à jour réussie, pour libérer le disque sans toucher aux autres services de l’hôte.

### Démarrage

23. En tant qu’administrateur, je veux qu’au démarrage du serveur l’instance se mette à jour puis démarre, pour qu’un serveur ne reste pas figé sur une vieille version.
24. En tant qu’administrateur, je veux qu’un échec ou « rien à faire » de la mise à jour au boot n’empêche pas l’instance de démarrer.
25. En tant qu’administrateur, je veux que `setup` installe et active l’unité systemd et que `uninstall` la retire, sans geste supplémentaire.
26. En tant qu’administrateur, je veux que l’unité ne relance pas en boucle infinie un démarrage qui échoue.

### Hôte partagé

27. En tant qu’administrateur d’un serveur qui héberge aussi ArgOS, je veux que l’orchestrateur et ArgOS ne se gênent pas (unités, utilisateurs, projets Compose, images, ports par défaut distincts), pour garder les deux sur la même machine en attendant des VM.
28. En tant qu’administrateur, je veux que `runtime` et `runner` se mettent à jour et démarrent même si Caddy ne peut pas prendre 80/443 (occupés par un autre service), pour que le conflit d’exposition ne bloque pas la mise à jour.
29. En tant qu’administrateur, je veux que `wap-runtime diagnostic` dise clairement quand 80/443 sont occupés par un autre service, pour comprendre pourquoi l’exposition web ne répond pas.

### Migration et docs

30. En tant qu’administrateur d’une instance 0.7.0, je veux savoir qu’il faut relancer `install.sh` une fois à la main pour passer à la CD, les mises à jour suivantes étant automatiques.
31. En tant que lecteur du README, je veux l’installation, `update`, le démarrage au boot, la cohabitation sur un hôte partagé, la visibilité ghcr et le nouveau check requis.
32. En tant que lecteur de la doc, je veux des entrées glossaire **CD**, **Staging**, **Promotion** et **Mise à jour de l’instance**.
33. En tant que lecteur futur, je veux un ADR 0013 qui ancre « images publiées sur ghcr, promotion du digest à la Release, mise à jour au démarrage et par commande ».

## Décisions d’implémentation

- **Registre** : `ghcr.io/ulyssoulv/wap-runtime` et `ghcr.io/ulyssoulv/wap-runner` ; multi-arch `linux/amd64,linux/arm64` (buildx + QEMU) ; label `org.opencontainers.image.source` vers le dépôt ; paquets publics (geste manuel unique documenté).
- **Job `images`** dans `ci.yml` : `needs: [pytest, vitest, sonar]`, seulement si la PR vient du dépôt (pas un fork), `packages: write` ; checkout du SHA de tête de la PR ; pousse `:sha-<sha>` et `:staging`. Script `orchestrator/scripts/publier-images-staging.sh` (ou équivalent), sur le modèle d’ArgOS. Check requis de la ruleset (documenté, posé à la main comme en 0.7.0).
- **Promotion** : workflow sur `release: published`, tag `orchestrator-vX.Y.Z` uniquement ; résout le SHA du tag ; `docker buildx imagetools create` de `:sha-<sha>` vers `X.Y.Z` et `latest` ; échoue si `:sha-<sha>` manque. Script `promouvoir-images-release.sh`. Pas de rebuild.
- **Installation** : `install.sh` sans `WAP_REF` résout la dernière Release `orchestrator-v*` non prerelease (API GitHub) et installe le paquet à ce tag. `setup` écrit `version` dans `config.toml` (`X.Y.Z` si le ref est un tag de Release, sinon le ref) et génère un compose avec `image: ghcr.io/ulyssoulv/wap-{runtime,runner}:<X.Y.Z | sha-<commit>>` ; si l’image n’existe pas sur ghcr, retombe sur `build:` au commit du paquet (ADR 0005).
- **`wap-runtime update`** (root) : version locale lue dans `config.toml` ; non semver → code 2. Cible = Release `orchestrator-vX.Y.Z` non prerelease la plus haute, strictement supérieure. Images `X.Y.Z` absentes sur ghcr → code 2 sans rien toucher. Session ouverte → code 1 avec la liste, sauf `--force`. Sinon : `pipx install --force` du paquet au tag (utilisateur d’instance), régénération du compose et de l’unité, `docker compose pull`, `up -d --wait --force-recreate`, mise à jour de `version`, suppression des anciennes images `ghcr.io/ulyssoulv/wap-*` seulement (jamais de `prune` global). Codes : 0 mise à jour faite, 2 rien à faire, 1 échec (journalisé, pas de rollback). Caddy non bloquant : code 0 si `runtime` et `runner` sont sains, avertissement si Caddy ne démarre pas.
- **Unité systemd `wap-runtime.service`** calquée sur `argos.service` : `Type=oneshot`, `RemainAfterExit=yes`, `Requires/After=docker.service`, `After/Wants=network-online.target`, `ExecStartPre=-+wap-runtime update`, `ExecStart=docker compose up -d --wait`, `ExecStop=docker compose down`, `TimeoutStartSec=infinity`, `Restart=on-failure` avec relances bornées (`StartLimitBurst` / `StartLimitIntervalSec`). Installée et activée par `setup`, retirée par `uninstall`. `restart: unless-stopped` reste dans le compose pour les crashs.
- **Cohabitation** : unité, utilisateur, dossier, projet Compose (`name: wap-runtime`) et images distincts d’ArgOS ; aucun chemin système ni port codé en dur ajouté. Le conflit 80/443 avec un autre service n’est pas résolu en 0.7.1 : `diagnostic` le signale.
- **Pas de jeton ghcr** sur les instances.
- **Version du paquet** : `0.7.1`.
- **Docs** : README (installation, `update`, boot, hôte partagé, visibilité ghcr, check `images`) ; glossaire **CD**, **Staging**, **Promotion**, **Mise à jour de l’instance** ; ADR 0013 (affine ADR 0002 et 0005).

## Décisions de test

- Bon test = comportement observable aux coutures : codes de sortie et effets de `wap-runtime update`, compose et unité générés par `setup`, sortie de `diagnostic` ; pas le détail des Dockerfile.
- **Couture principale** : CLI `wap-runtime` avec les fakes déjà en place (faux `docker`), plus faux `pipx`, faux `systemctl` et API des Releases factice. Cas : choix de la Release (semver le plus haut, préfixe `orchestrator-v`, prereleases exclues) ; version locale non semver → 2 ; images absentes → 2 sans rien toucher ; session ouverte → refus, `--force` passe ; succès → 0 avec paquet, compose, `version` mis à jour et anciennes images `wap-*` seules supprimées ; échec de pull ou de recreate → 1 ; Caddy en échec → 0 avec avertissement.
- **Installation** : compose avec `image:` ghcr quand l’image existe, `build:` sinon ; `version` écrite dans `config.toml` ; unité systemd écrite et activée par `setup`, retirée par `uninstall`.
- **Diagnostic** : 80/443 occupés par un autre processus signalés.
- Les workflows (`images`, promotion) et la visibilité ghcr se vérifient aux tests humains, sur la vraie PR et la vraie Release, comme la CI en 0.7.0.
- Suites 0.1.0–0.7.0 restent vertes.
- Tests humains : PR verte → `:sha-<sha>` et `:staging` sur ghcr, multi-arch, publics ; installation `WAP_REF=<branche>` qui tire sans build ; après Finalise, `X.Y.Z` et `latest` = même digest ; `sudo wap-runtime update` sur une instance en retard (0), à jour (2), avec session ouverte (refus) ; reboot du serveur → mise à jour puis démarrage ; serveur partagé avec ArgOS → les deux services tournent, `diagnostic` explique 80/443.

## Notes

- Modèle : ArgOS 0.7.2 (`argos.service`, `mettre-a-jour-le-site.sh`, `publier-images-staging.sh`, `promouvoir-images-release.sh`). Écart assumé : ici staging et promotion sont automatiques, parce que `:sha-<sha>` est publié sur chaque PR verte (avant les tests humains) et que la Release pointe déjà sur ce SHA.
- La Release reste créée par `/crel` / Finalise ; la CD réagit à sa publication.
- Le conflit 80/443 avec ArgOS existe déjà depuis la 0.6.0 sur un hôte partagé ; il disparaîtra avec une VM par service.
