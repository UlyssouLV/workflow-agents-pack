# V0.2.0 — Provisionnement self-hosted (Linux + CLIs)

## Problème

L’orchestrateur doit tourner sur la machine hôte de l’utilisateur (un serveur Linux à lui, pas un VPS imposé), mais rien ne permet aujourd’hui de préparer cette machine : il faut installer à la main Docker, `git`, `gh`, les CLIs agents (`claude`, `agent`), créer une configuration d’instance, récupérer le pack et démarrer des services, sans savoir si le résultat est sain ni s’il survivra à un redémarrage. `orchestrator/` ne contient encore qu’une suite de tests de frontière : pas de paquet, pas de CLI, pas de service.

## Solution

Une **seule commande, sans interaction**, lancée sur un Debian 12+ / Ubuntu 22.04+ :

```bash
curl -fsSL https://raw.githubusercontent.com/UlyssouLV/workflow-agents-pack/feat/runtime-orchestrator/orchestrator/install.sh | sudo bash
```

L’URL pointe sur la branche de base (elle ne bouge qu’au « Finalise » : toujours la dernière version livrée). `install.sh` est un bootstrap bash minimal : il vérifie la plateforme, installe Python/pipx, crée l’**utilisateur système `orchestrator`**, installe le paquet Python `wap-runtime` (depuis la même branche) et lance `wap-runtime setup`. Ce dernier, **idempotent** (le relancer répare / met à niveau) :

1. installe le socle manquant par les méthodes officielles, sans réinstaller ce qui est présent : `git` (apt), Docker Engine + plugin Compose (dépôt apt Docker, `systemctl enable docker`), `gh` (dépôt apt GitHub CLI), `claude` et `agent` (installeurs officiels, pour l’utilisateur `orchestrator`) — **sans authentification** ;
2. crée l’instance `/home/orchestrator/.wap-runtime/` (`config.toml`, `secrets.env`, `compose.yaml`, `pack/`) ;
3. clone ou met à jour le pack (`pack_ref`, `main` par défaut) dans `pack/` ;
4. construit localement l’image du service `runtime` et démarre Compose (`restart: unless-stopped`) ;
5. attend que `GET /health` réponde OK (délai maximum) et l’affiche.

Après un reboot, Docker (activé) relance le service sans unité systemd maison. `wap-runtime health` interroge le healthcheck ; `wap-runtime uninstall` arrête et retire le Compose (`--purge` supprime aussi l’instance), sans toucher à Docker ni aux CLIs.

## User stories

1. En tant qu’utilisateur avec un serveur Debian/Ubuntu, je colle une commande, je n’ai rien à répondre, et à la fin l’orchestrateur tourne et m’affiche son healthcheck OK.
2. En tant qu’utilisateur, je redémarre ou j’éteins puis rallume le serveur : le service runtime repart seul.
3. En tant qu’utilisateur, je relance la même commande : rien n’est réinstallé inutilement, mes valeurs modifiées dans `config.toml` et mon `secrets.env` sont conservés, le pack est mis à jour.
4. En tant qu’utilisateur sur une distribution ou une version non supportée, l’installation s’arrête tout de suite avec un message clair et un code ≠ 0.
5. En tant qu’utilisateur dont l’installation échoue, je sais quelle étape a échoué, j’ai un log complet dans `/var/log/wap-runtime/install.log`, et je peux relancer avec `WAP_DEBUG=1` pour une trace détaillée.
6. En tant qu’utilisateur, je choisis le port ou la branche du pack sans interaction via `WAP_PORT` / `WAP_PACK_REF`.
7. En tant qu’utilisateur, `wap-runtime health` me dit en une ligne (et par son code de sortie) si le runtime répond.
8. En tant qu’utilisateur, `wap-runtime uninstall` retire le service pour repartir propre ; `--purge` efface aussi l’instance.
9. En tant qu’administrateur d’un serveur partagé, rien ne tourne en root à l’exécution, le runtime n’écoute que sur `127.0.0.1`, et les autres services du serveur ne sont pas touchés.

## Décisions d’implémentation

- **Paquet Python** `orchestrator/` avec `pyproject.toml` (nom `wap-runtime`, point d’entrée console `wap-runtime`), Python **≥ 3.10** côté hôte. Sous-commandes : `setup`, `health`, `uninstall [--purge]`. Les dépendances de dev passent dans le `pyproject.toml` (extra `dev`) ; la suite pytest de la 0.1.0 reste sous `orchestrator/tests/`.
- **Bootstrap** `orchestrator/install.sh` : `set -euo pipefail`, doit être root (sinon message `… | sudo bash`), `DEBIAN_FRONTEND=noninteractive`, aucun prompt. Plateformes : Debian 12+ / Ubuntu 22.04+ via `/etc/os-release`, sinon arrêt. Installe `python3`, `pipx`, `git` ; crée l’utilisateur système `orchestrator` (avec home) ; installe `wap-runtime` via pipx pour cet utilisateur depuis `git+https://github.com/UlyssouLV/workflow-agents-pack@feat/runtime-orchestrator#subdirectory=orchestrator` ; lance `wap-runtime setup`.
- **Utilisateur d’instance `orchestrator`** : membre du groupe `docker` ; propriétaire de `/home/orchestrator/.wap-runtime/` ; les CLIs `claude` / `agent` sont installés pour lui. Les étapes système (apt, dépôts, groupe, `systemctl`) s’exécutent en root, le reste en `orchestrator`.
- **Plan d’installation** : `setup` détecte l’état (binaires présents, fichiers d’instance existants) et en déduit une liste d’étapes à exécuter ; l’exécution est une couche mince d’appels système. Le plan est la surface testée.
- **Instance `~/.wap-runtime/`** :
  - `config.toml` — `port` (défaut `8787`), `pack_ref` (défaut `main`), `pack_path`, `version` ; les variables `WAP_PORT` / `WAP_PACK_REF` s’appliquent à la création ; un `setup` relancé complète les clés manquantes sans écraser les valeurs existantes ;
  - `secrets.env` — créé vide en `0600`, jamais réécrit ;
  - `compose.yaml` — généré à chaque `setup` depuis `config.toml` ;
  - `pack/` — clone du pack, aligné sur `pack_ref` à chaque `setup`.
- **Service `runtime`** : `orchestrator/Dockerfile` (Python 3.12), image construite localement par `setup` (pas de registry). Expose `GET /health` → JSON `{"status": "ok", "version": "<x.y.z>"}`. Publié sur `127.0.0.1:<port>` uniquement, `restart: unless-stopped`.
- **Healthcheck** : `wap-runtime health` appelle `/health`, sort en `0` si OK, `≠ 0` sinon. `setup` attend l’OK avec un délai maximum puis échoue avec un message s’il ne vient pas.
- **Journalisation / debug** : chaque étape est journalisée dans `/var/log/wap-runtime/install.log` ; `WAP_DEBUG=1` active `set -x` côté bash et des logs verbeux côté Python. Un échec nomme l’étape, renvoie au log, sort `≠ 0`.
- **Docs** : ADR 0002 (installation via la branche de base en `sudo bash`, utilisateur dédié `orchestrator`, Compose + restart policy) ; glossaire (*provisionnement*, *utilisateur d’instance*) ; README (commande d’installation, prérequis, debug, désinstallation).

## Décisions de test

- pytest, sans vrai Docker ni sudo : faux binaires dans un `PATH` temporaire, `HOME` temporaire pour l’instance, faux `/etc/os-release`.
- **Plan** : avec tel binaire présent / absent, l’étape correspondante est planifiée ou non ; distribution non supportée → arrêt avec message.
- **Instance** : création des fichiers, `secrets.env` en `0600`, idempotence (un second `setup` ne modifie ni `secrets.env` ni une valeur éditée dans `config.toml`), `WAP_PORT` / `WAP_PACK_REF` pris en compte, `compose.yaml` publié sur `127.0.0.1` avec `restart: unless-stopped`.
- **`/health`** testé en process (serveur HTTP lancé dans le test) ; `wap-runtime health` testé contre ce serveur et contre un port fermé (code de sortie).
- **`uninstall`** : sans `--purge` l’instance reste, avec `--purge` elle disparaît.
- La suite de frontière de la 0.1.0 reste verte.
- Le vrai `curl … | sudo bash`, le reboot et l’uninstall sur une VM Debian/Ubuntu propre : ticket de tests humains.

## Hors périmètre

- Authentification des CLIs (`gh`, `claude`, `agent`).
- Choisir un seul CLI agent à installer (les deux sont installés).
- Autres distributions (Fedora, Arch…) ; la liste des distributions supportées sera documentée sur la future `main`.
- CI de build / publication de l’image runtime.
- Mise à jour CI/CD des serveurs déjà installés.
- Tunnel / accès distant, exposition hors `127.0.0.1`.
- Dashboard / cockpit, registry de repos métier (0.3.0), actions métier (`/implement`…), mapping skills → prompts headless, autopilot.
- Installer le pack dans des repos métier ou au niveau utilisateur (`~/.claude/skills/`).
